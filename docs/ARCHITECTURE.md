## 1. Общая схема

```
Пользователь в MAX (телефон, веб)
        │  открывает мини-приложение по кнопке бота
        ▼
┌───────────────────────┐   /api/*   ┌──────────────────────────────────────┐
│ frontend: React + nginx│──────────▶│ backend: Spring Boot, модульный монолит│
│ статика мини-приложения│            └──┬──────────┬───────────┬──────────┬─┘
└───────────────────────┘               │          │           │          │
                                        ▼          ▼           ▼          ▼
                                   PostgreSQL    MinIO      GigaChat   MAX Bot API
                                   метаданные    файлы     (исходящие  (исходящие
                                                            вызовы)    + webhook)
```

- Мини-приложение и API — на одном адресе: nginx отдаёт статику и проксирует `/api/`.
- GigaChat и MAX Bot API вызывает только бэкенд. У модели нет доступа ни к базе,
  ни к хранилищу.
- Входящий трафик от MAX — только webhook бота на стенде.

## 2. Бэкенд

### Стиль

**Модульный монолит, пакеты по функциям.** Один Spring Boot сервис, внутри —
модули в `ru.sibvibe.approval.<модуль>`. Внутри модуля — обычный Spring:
`Controller → Service → Repository`.

**Порты — только на границах с внешними системами**, их пять: хранилище, извлечение
текста, модель, проверка личности, отправка уведомлений. Полную «гексагональную»
архитектуру с портами на всё не делаем: за две недели это обёртки ради обёрток.
Порт нужен там, где реализация может смениться или её нужно подменить в тестах.

### Внутри модуля

**Слои, не гексагональная архитектура.** Порты — только на границах с внешними
системами (раздел «Порты»); всё остальное — классический Spring:

```
<модуль>/
├── controller/   принимает HTTP-запросы и отдаёт ответы
├── dto/          формы данных запросов и ответов (record) — то, что видит фронтенд
├── service/      бизнес-логика, транзакции, проверка прав — вход для других модулей
├── entity/       JPA-сущности и перечисления модуля — то, что лежит в базе
├── repository/   Spring Data репозитории
├── adapter/      реализации портов — только в storage, ai, security, bot
└── <Порт>.java   интерфейс порта в корне модуля, как ai/DocumentExtractor.java
```

- Вызовы идут сверху вниз: `controller → service → repository`. Контроллер не ходит в репозиторий.
- **Другой модуль вызывает только `service/`** — не `repository/` и не `entity/` чужого модуля.
- **Между модулями связь по id, без JPA-ассоциаций:** `Document.authorId`, а не
  `@ManyToOne AppUser`. Так сущности модулей не срастаются и владельцы не мешают друг другу.
- Внутри модуля ассоциации JPA — пожалуйста.

### Модули

| Пакет | Отвечает за | Владелец | Может вызывать |
|---|---|---|---|
| `common` | Ошибки, текущий пользователь, время, общие DTO | оба, ревью друг у друга | — |
| `security` | Проверка `initData`, фильтр запросов, демо-режим | Никита | `common`, `organization` |
| `organization` | Компании, участники, роли, приглашения, заявки, шаблоны маршрутов | Никита | `common` |
| `document` | Документы, версии, файлы версий, списки, выдача файлов | Илья | `common`, `organization`, `storage`, `rules`, `ai` |
| `storage` | Порт `FileStorage` и реализация на MinIO | Илья | `common` |
| `rules` | `RuleEngine`, правила и их источники | Илья | `common` |
| `ai` | Порты `TextExtractor`, `DocumentExtractor`, `DocumentClassifier`, маскирование, GigaChat | Илья | `common` |
| `approval` | Предпросмотр маршрута, отправка, решения, состояния документа | Никита | `common`, `organization`, `document` |
| `bot` | Порт `Notifier`, отправка уведомлений, приём webhook | Никита | `common`, `organization`, `document` |

Правила:
- **Модуль обращается к чужим данным только через сервис этого модуля**, не через
  его репозиторий. Так модули не ломают друг другу инварианты.
- **Read-модель документов — узкое исключение для чтения.** `DocumentReadRepository`
  может читать таблицы `approval` и `organization` одним SQL-запросом, чтобы применить ACL
  до `count`, фильтров и пагинации. Она не изменяет чужие таблицы; команды по-прежнему
  проходят через сервисы модулей-владельцев.
- **`bot` не вызывается напрямую** из `approval` и `organization`. Они публикуют
  доменные события, `bot` на них подписан — см. «Уведомления». Название документа для текста
  уведомления кладёт в событие сам `approval` (`ApprovalRequestedEvent.documentTitle`,
  `DocumentDecidedEvent.documentTitle`) — `bot` не запрашивает его отдельным вызовом.
- **Исключение — `document.DocumentLookup`**: статус документа текстовым запросом
  в боте. `bot` вызывает его напрямую, как обычный сервис другого модуля из таблицы «Может
  вызывать» — это не «обращённая зависимость» ниже: там интерфейс лежит у нуждающегося модуля,
  потому что тот не может звать владельца данных напрямую; здесь `document` и определяет,
  и реализует порт сам, а `bot` просто его законный вызывающий.
- Изменение `common` — только через PR с ревью второго бэкендера.
- **Обращённые зависимости.** Когда `organization` нужен ответ от модуля, который вызывает
  его самого, интерфейс лежит в `organization`, а реализует его тот модуль: `DocumentTypeDirectory`
  (id типов документов по кодам, для маршрутов по умолчанию) реализует `document`,
  `PendingStepsGuard` (вернуть авторам документы, где исключённый или лишённый роли человек ещё не решил) — `approval`. Это не порты
  на внешнюю систему, а способ не нарушить таблицу «Может вызывать».
- **Статус документа при согласовании меняет только `document.DocumentStateService`.** `approval` вызывает его
  и в сущность `Document` не пишет. Сервис принимает вызовы только внутри транзакции вызывающего под блокировкой
  строки документа и сам проверяет переходы по таблице раздела 4. Наружу он отдаёт не сущность, а `DocumentState`
  и `DocumentSnapshot`: `approval` не импортирует `document.entity` (это проверяет `ModuleBoundariesTest`).

### Порты

| Порт | Пакет | Реализация MVP | Зачем порт |
|---|---|---|---|
| `FileStorage` | `storage` | MinIO | Подмена в тестах, смена хранилища |
| `TextExtractor` | `ai` | PDFBox + JDK для DOCX | Новые форматы без изменения конвейера |
| `DocumentExtractor` | `ai` | Spring AI + GigaChat | Поля (`extract`) и краткая сводка (`summarize`) — раздельными вызовами, последовательно (личный аккаунт GigaChat держит один поток); смена провайдера настройкой |
| `DocumentClassifier` | `ai` | Spring AI + GigaChat | Вид документа по тексту при загрузке с «определить автоматически»; недоступна модель — «Другой документ» |
| `MaxIdentityVerifier` | `security` | HMAC-SHA256 по секрету бота | Тесты без настоящего MAX |
| `Notifier` | `bot` | MAX Bot API | Тесты и отключение уведомлений |

### Текущий пользователь

Фильтр в `security` на каждом запросе:
1. Проверяет подпись `initData` и её давность → `max_user_id`.
2. Находит или создаёт `AppUser`.
3. Если пришёл `X-Demo-Act-As` — проверяет, что демо-режим включён и этот участник
   из **демо-песочницы самого вызывающего** (см. «Демо-режим»), и подменяет пользователя.
4. Загружает из базы членство и роли — **на каждом запросе**, без кэша: снятая роль
   действует сразу.

Результат — объект `CurrentUser` (`userId`, `memberId`, `orgId`, `roleIds`, `isAdmin`),
доступный сервисам. Сервисы берут пользователя только оттуда.

### Транзакции

**Никаких внешних вызовов внутри транзакции базы** — ни модели, ни MinIO, ни Bot API.
Иначе медленный ответ модели держит соединение, и пул соединений кончается
на нескольких одновременных загрузках.

Загрузка версии документа:
1. Файлы кладутся в MinIO — вне транзакции.
2. Транзакция: документ, версия, файлы версии → commit. У типа с проверкой
   `check_status = FAILED` сразу: если процесс упадёт до шага 4, версия честно
   останется «проверка не выполнена», а не `null`.
3. Извлечение текста, полей и краткой сводки моделью — вне транзакции, с тайм-аутом.
4. Транзакция: результаты проверки на версию, `check_status = CHECKED` → commit.
5. Ответ клиенту. Упал шаг 3 — документ всё равно сохранён, `modelAvailable = false`,
   правила проверены по полям, введённым вручную.

Файлы, загруженные в MinIO при упавшем шаге 2, остаются без ссылок. В MVP это допустимо.

### Конкурентность

- **Любое изменение состояния документа — отправка, решение, новая версия — идёт
  в одной транзакции под блокировкой строки документа** (`PESSIMISTIC_WRITE`,
  то есть `SELECT … FOR UPDATE`). Параллельные решения по одному документу
  выполняются по очереди, а не одновременно.
- Решение принимается, только если шаг в состоянии `PENDING` и его этап активен.
- **Повтор того же решения тем же пользователем** (двойной клик, повтор запроса) —
  200 с текущей карточкой, без изменений.
- **«Согласовать» и «Вернуть» одновременно на параллельном этапе:** выигрывает
  первый, взявший блокировку. Если первым был возврат — этап закрыт, шаг второго
  получил `SKIPPED`, и второй получает 409 `STEP_NOT_ACTIVE` с текстом «Документ уже
  возвращён». Если первым было согласование — возврат проходит как обычно.
- Использование личной ссылки — один атомарный `UPDATE … WHERE used_at IS NULL …`.
- Уникальность, которую нельзя проверять кодом «прочитал — записал», держат
  ограничения базы: одна ожидающая заявка на пользователя, один активный участник
  на пользователя, один активный код компании.

### Уведомления

`organization` и `approval` публикуют доменные события — «заявка подана», «документ
ждёт решения», «документ возвращён» и т. д. Модуль `bot` слушает их через
`@TransactionalEventListener(phase = AFTER_COMMIT)` и отправляет через `Notifier`.

Так уведомление уходит только после того, как изменение действительно сохранилось,
а ошибка Bot API не откатывает действие пользователя: её пишем в лог.

**Напоминание о застрявшем шаге** (COULD) — не событие внутри пользовательского запроса,
а `approval.StuckStepReminderJob`: раз в сутки (`@Scheduled`, `app.reminders.cron`) находит шаги,
которые висят в `PENDING` дольше `app.reminders.stuck-after-hours`, атомарно помечает их напомненными
(тем же приёмом, что и использование личной ссылки, раздел «Конкурентность») и публикует
`StuckStepReminderEvent` — не чаще раза в `app.reminders.cooldown-hours` на шаг. Для демо оба порога
снижаются настройкой, без правки кода и без ожидания суток.

### Ошибки

Сервис бросает `DomainException(code, httpStatus, message)`, `@RestControllerAdvice`
превращает её в `{ code, message, details }`. Коды и статусы — в API_CONTRACTS.md.
`message` пишется для пользователя, по-русски.

### Профили

- По умолчанию — боевые настройки. Принимается только подписанная `initData`.
- `dev` — дополнительно принимает `Authorization: Dev <maxUserId>` для работы
  без MAX. На стенде и в сборке для проверяющих профиль `dev` не включается.

## 3. Модель данных

Имена сущностей — PascalCase, таблицы — snake_case. Схемой управляет Liquibase,
Hibernate в режиме `validate`. Слитый в `main` changeset не редактируется.

| Сущность | Поля |
|---|---|
| `AppUser` | id, **max_user_id** (unique), full_name, created_at — только личность |
| `Organization` | id, name, inn (необязательный, не проверяется), created_by, created_at, **is_demo**, **demo_owner_id** → AppUser (у демо-песочницы — чья она), **city**, **time_zone** (только пояса России; по нему «сегодня» для правил, периодов и показателей) |
| `OrganizationMember` | id, org_id, user_id, **status** (ACTIVE / DISABLED), **is_admin**, joined_at, **is_demo** (техническая копия признака организации); unique(org_id, user_id); не более одного ACTIVE на пользователя среди реальных компаний |
| `Role` | id, org_id, code, name — **только предметные роли**: Директор, Юрист, Бухгалтер… Права администратора — не роль |
| `MemberRole` | member_id, role_id, **granted_by, granted_at** |
| `Invite` | id, org_id, **kind** (ORG_CODE / PERSONAL_LINK), code или token, created_by, created_at, expires_at, used_at, used_by, revoked_at |
| `InviteRole` | invite_id, role_id — роли для личной ссылки |
| `JoinRequest` | id, org_id, user_id, invite_id, **status** (PENDING / APPROVED / REJECTED / CANCELLED), created_at, decided_by, decided_at |
| `DocumentType` | id, name, code, **is_generic** |
| `DocumentTypeField` | id, document_type_id, field_name, field_type, label, hint, **position** (порядок показа) |
| `ApprovalRoute` | id, document_type_id, org_id, **stage_order**, **role_id**, **is_mandatory** |
| `RequirementRule` | id, document_type_id, field_name, description, check_type, expected, **kind**, severity, source_title, source_url, source_ref, source_checked_at |
| `OrganizationRuleSetting` | **org_id + rule_id** (PK), enabled, severity, description, source_title, source_ref, expected, updated_by, updated_at — отличие правила компании от шаблона; `NULL` — как в шаблоне, строки нет — правило целиком как в шаблоне |
| `Document` | id, document_type_id, author_id, org_id, **title**, status, current_stage, **current_version_no**, visibility, **type_auto_detected** (тип выбрал ИИ), created_at, updated_at |
| `DocumentVersion` | id, document_id, **version_no**, **contains_sensitive**, content (jsonb, у документа-формы), created_by, created_at, extracted_fields (jsonb), validation_issues (jsonb), **ai_summary** (проверенная краткая сводка или null), **check_status** (`CHECKED` / `FAILED`; null у типа с `is_generic = true`; с  таких типов нет — «Другой документ» (`GENERIC`) тоже проверяется), **withdrawn_at** (автор отозвал версию с согласования) |
| `DocumentFile` | id, version_id, **kind** (MAIN / ATTACHMENT), position, storage_key, file_name, mime_type, file_size, created_at |
| `ApprovalStep` | id, document_id, **version_no**, approver_id, **role_id**, **stage_order**, **origin** (TEMPLATE / ADDED_BY_AUTHOR), decision, **auto_reason**, comment, created_at, **activated_at** (этап стал активным), decided_at, **last_reminded_at** (напоминание о застрявшем шаге,; `null` — ни разу) |

Значения:
- `Document.status`: `DRAFT` / `IN_APPROVAL` / `APPROVED` / `RETURNED` / `REJECTED`.
- `ApprovalStep.decision`: `PENDING` / `APPROVED` / `RETURNED` / `REJECTED` / `SKIPPED`.
- `ApprovalStep.auto_reason`: `null`, `AUTHOR_HOLDS_ROLE` или `CARRIED_OVER` (у `APPROVED`), `MEMBER_REMOVED`
  (у `SKIPPED`) — см. «Маршрут». Соответствие отметки и решения проверяет ограничение в БД (миграция 011).
- `Document.visibility`: `PRIVATE` (автор и все, у кого есть шаг по документу в любой версии) / `ORG` (вся компания —
  **после отправки**: черновик видит только автор и те, у кого был шаг в прошлых версиях).
- `RequirementRule.kind`: `LEGAL` / `INTERNAL_POLICY` / `PRODUCT_RULE`.

Почему так:
- `OrganizationMember.is_demo` нужен для частичного уникального индекса по `user_id`
  при `status = 'ACTIVE' AND NOT is_demo`: предикат индекса PostgreSQL не может читать
  другую таблицу. Составной FK `(org_id, is_demo) → Organization(id, is_demo)` гарантирует
  совпадение признака с организацией. Так членство в демо-песочнице не мешает реальной компании.
- **Права администратора — флаг участника, а не роль.** Роли используются в маршрутах;
  если бы администратор был ролью, его можно было бы поставить согласующим,
  он попадал бы в выбор ролей, и проверки «последнего администратора» и «через
  ссылку администратора не выдать» пришлось бы писать как исключения.
- **Признак чувствительных данных — у версии.** Первая версия может быть без
  персональных данных, а исправленная — с ними. Решение «отправлять ли текст в модель»
  принимается для конкретного содержимого.
- **Отдельной таблицы журнала нет:** история выводится из версий, шагов, заявок
  и выдачи ролей.

## 4. Состояния документа

| Из | Действие | В | Что происходит |
|---|---|---|---|
| — | Создать | `DRAFT` | Версия 1, проверка правил |
| `DRAFT` | Новая версия, правка полей | `DRAFT` | Проверка заново |
| `DRAFT` | Отправить | `IN_APPROVAL` | Шаги для текущей версии, активен этап 1 |
| `IN_APPROVAL` | Все шаги этапа согласованы | `IN_APPROVAL` | Активен следующий этап |
| `IN_APPROVAL` | Согласован последний этап | `APPROVED` | Документ неизменяем |
| `IN_APPROVAL` | Вернуть | `RETURNED` | Остальные ожидающие шаги версии → `SKIPPED` |
| `IN_APPROVAL` | Отклонить | `REJECTED` | Остальные ожидающие шаги версии → `SKIPPED` |
| `IN_APPROVAL` | Автор отзывает с согласования | `RETURNED` | Ожидающие шаги версии → `SKIPPED`, `document_version.withdrawn_at`; дальше как после возврата |
| `RETURNED` | Новая версия | `DRAFT` | Проверка заново; шаги прошлой версии остаются в истории |
| `IN_APPROVAL` | Согласующего исключили или сняли роль | `RETURNED` | Его шаги → `SKIPPED` + `MEMBER_REMOVED`, остальные ожидающие → `SKIPPED` |
| `APPROVED`, `REJECTED` | — | — | Конечные состояния |

- Возвращённая версия не редактируется: она уже в истории, согласующие видели именно её.
  Любое исправление — новая версия, в том числе если меняются только поля.
- Повторная отправка создаёт новый набор шагов для новой версии и начинает с этапа 1.
- **Одобрения прошлой версии сохраняются, если содержимое то же** (`CarriedApprovals`):
  одобрение относится к содержимому — файлам (по `storage_key`: файлы неизменяемы) и значениям полей. Если новая
  версия с предыдущей совпадает, шаг того же человека в той же роли сразу `APPROVED` с `auto_reason = CARRIED_OVER`.
  Так бывает, когда автор отозвал документ ради маршрута или согласующего исключили. Изменилось хоть что-то —
  согласуют все: прежнее «согласовано» к новому тексту не относится. Чтобы повторное согласование было быстрым,
  карточка показывает разницу с прошлой версией (`VersionChangesService`, `DocumentCard.changes`).
- **Исключение согласующего или снятие роли не блокируется**: документы, где он ещё не решил,
  возвращаются авторам — его шаги `SKIPPED` + `MEMBER_REMOVED`, остальные ожидающие `SKIPPED`, событие
  `ApproverRemovedEvent`. Раньше действие запрещалось (`MEMBER_HAS_PENDING_STEPS`), и администратор ждал решения
  того, кого исключает.

**Как движок ведёт документ по маршруту** (`approval`: `RoutePlanner`, `SubmissionService`, `DecisionService`):
- При отправке шаги создаются **сразу для всех этапов версии**. `activated_at` ставится только шагам активного
  этапа, `document.current_stage` — номер активного этапа. Шаги автосогласованного автора (`AUTHOR_HOLDS_ROLE`)
  создаются уже `APPROVED`, `activated_at = decided_at` — момент отправки.
- Необязательный участник без кандидатов шага не получает: в предпросмотре он «пропускается». Этап, где никого не
  осталось, просто не создаётся; активным становится первый этап, где есть кому решать.
- **Решать некому вообще** (обязательные роли только у автора, остальное пропущено): документ становится
  «Согласован» тут же при отправке, шаг автора виден в истории с отметкой `AUTHOR_HOLDS_ROLE`.
- Этап закрыт, когда одобрены **все** его шаги (AND). Тогда активным становится следующий этап, где есть ожидающие
  шаги, а этапы без них перескакиваются; если таких нет — документ «Согласован».
- «Вернуть» и «отклонить» — fail-fast: все остальные ожидающие шаги версии, включая будущие этапы, получают
  `SKIPPED`; `current_stage = NULL`.
- Решение адресуется шагу. Шаг читается только после блокировки документа: до неё читается лишь id документа, иначе
  кэш сессии сохранил бы состояние, которое устарело, пока решение ждало очереди.
- Маршрут по умолчанию, если его у компании ещё нет, создаётся при первом предпросмотре или отправке вставкой
  `ON CONFLICT DO NOTHING`: два параллельных первых обращения оба успешны, строк ровно по одной.
- Изменяющие вызовы публикуют события `ApprovalRequestedEvent` («документ ждёт вашего решения») и
  `DocumentDecidedEvent` (согласован, возвращён, отклонён). Слушатели бота — только с `AFTER_COMMIT`.

## 5. Маршрут

При предпросмотре и отправке:
1. Берётся шаблон маршрута для пары «тип документа + компания».
2. Для каждого участника шаблона ищутся **активные участники компании с этой ролью**,
   кроме автора.
3. Кандидатов нет:
   - участник необязательный (`is_mandatory = false`) — пропускается;
   - обязательный, и **роль есть у самого автора** — шаг создаётся сразу согласованным
     с `auto_reason = AUTHOR_HOLDS_ROLE` и в истории виден как «согласовано автором
     как Директор»;
   - обязательный, и роли нет ни у кого — отправка невозможна, `ROUTE_ROLE_EMPTY`.
4. Кандидат один — подставляется. Несколько — выбирает автор.
5. **Шаблон только предзаполняет маршрут.** Автор в конструкторе ставит людей в любом порядке и в любые
   этапы, добавляет кого угодно из активных носителей ролей и убирает всех, кроме **обязательных** (`is_mandatory`
   теперь значит ещё и «нельзя удалить»). Сервер проверяет: обязательные роли на месте (роль закрыта, если в маршруте
   есть её носитель), один человек — один раз, нет пустых этапов. Этапы нумеруются подряд с 1.
6. **Утверждение.** Последним может стоять один утверждающий — шаг `kind = ENDORSEMENT` отдельным этапом.
   По умолчанию конструктор ставит туда последний этап шаблона, если в нём один человек. «На утверждении» и
   «Утверждён» не хранятся в `document.status`: их вычисляет выражение `DocumentReadRepository.DISPLAY_STATUS`,
   одно на список, фильтр, карточку и бота.
7. **Повторная отправка.** Предпросмотр отдаёт маршрут прошлой отправленной версии (`previous`) — им, а не
   шаблоном, заполняется конструктор; решения сбрасываются.

   Шаг, который был создан, обязателен для закрытия этапа независимо от `is_mandatory`: этап из двух необязательных
   участников иначе закрылся бы без единого решения. Человек в маршруте — один элемент с одной ролью: раньше
   человек с двумя ролями этапа получал два шага, теперь стоит один раз.

Почему автор не согласует сам, если есть кто-то ещё: это смысл согласования —
второй взгляд. Почему автоматическое согласование, когда больше некому: в маленькой
компании директор пишет служебные записки сам, и маршрут не должен становиться
непроходимым. Отметка в истории делает это прозрачным, а не скрытым.

### Роли и маршруты новой компании

Создатель компании получает права администратора и роль «Директор». Маршруты
по умолчанию **консервативные**: необязательные этапы пропускаются, если в компании
нет такой роли. Поэтому компания из двух человек может работать сразу.

| Тип | Код типа | Маршрут по умолчанию |
|---|---|---|
| Служебная записка | `OFFICIAL_MEMO` | Руководитель отдела (необязательно) → Директор |
| Заявление на отпуск | `VACATION_REQUEST` | Кадровик (необязательно) → Директор |
| Заявка на меру поддержки | `SUPPORT_MEASURE_REQUEST` | Юрист и Бухгалтер параллельно (оба необязательно) → Директор |
| Заявка на командировку | `BUSINESS_TRIP_REQUEST` | Руководитель отдела (необязательно) → Бухгалтер (необязательно) → Директор |
| Другой документ | `GENERIC` | Директор (необязательно — по умолчанию обязательных нет; администратор может отметить) |

Роли по умолчанию (`DIRECTOR`, `DEPARTMENT_HEAD`, `LAWYER`, `ACCOUNTANT`, `HR`): Директор,
Руководитель отдела, Юрист, Бухгалтер, Кадровик.

**Откуда берутся типы и как маршруты попадают в компании.**
- Сами типы (`name`, `code`, `is_generic`) создаёт миграция `17-001-default-document-types`
  (`ON CONFLICT (code) DO NOTHING`). Маршрут ссылается на тип, поэтому без строки в `document_type`
  маршрута не бывает.
- **Справочник** добавляет поля и правила проверки к этим типам, находя тип по `code`, и **не вставляет
  те же типы заново без `ON CONFLICT`** — иначе миграция упадёт при старте. Коды — договорённость между  и.
- Маршруты создаются при создании компании для типов, которые есть в базе.
- **Добор при старте.** Если типы появились позже компаний, `RouteBackfillRunner` при каждом старте вызывает
  `RouteTemplateService.backfillAllOrganizations`: настоящим компаниям, у которых для типа ещё нет маршрута,
  создаётся маршрут по умолчанию. Вызов идемпотентен, порядок слияния задач значения не имеет, а сбой добора
  не мешает запуску. Демо-песочницы добор пропускает: их маршрут задаёт справочник.

*SHOULD* — добавлять и переименовывать роли. Редактор состава шаблона (этапы, роли на этапах, их порядок) —
`RouteTemplateService.replaceTemplate`, `PUT /orgs/current/routes/{documentTypeId}`; отдельный экран
`RouteTemplateScreen` (`/company/routes/:typeId`, — не панель поверх «Компании»: закреплённое
«Сохранить», подтверждение выхода без сохранения). Полная замена: позиция этапа в присланном списке становится
его номером; шаблон без единой роли сервер отвергает — иначе он неотличим от «ещё не создан» и был бы молча
восстановлен по умолчанию на следующем обращении. Метод берёт блокировку строки компании
(`organizationRepository.findByIdForUpdate`), как `CompanyService.updateLocation`: без неё два одновременных
сохранения не видят строк друг друга. В отличие от `setMandatory` и от конструктора маршрута документа,
здесь администратор убирает и переставляет **любую** роль, включая обязательные — запрет «обязательную не убрать»
действует только на автора документа при отправке, а не на администратора, который меняет сам шаблон. Шаблон
«Другого документа» (`GENERIC`) редактируется наравне с остальными: по умолчанию обязательных
нет — маршрут составляет автор, — но компания может отметить, например, Директора; тогда в обход обязательных не уйти
ни выбором «Другого документа», ни сканом без текста (он тоже становится «Другим документом»).

**Новый тип документа — это данные, а не код («Заявка на командировку»).** Четвёртый тип добавлен без
единого нового класса и без правки конвейера; проверка и маршрут берут всё из справочника:
1. `testdata/rules.json` — поля и правила типа, `python testdata/generate.py` — тестовые документы, `expected.json`
   и `docs/RULES.md`;
2. миграция справочника (`013-business-trip-request.sql`): строка в `document_type`, поля, правила; текст в ней
   совпадает с `rules.json`, это построчно проверяет `DatabaseSchemaTest`;
3. маршрут по умолчанию — одна запись в `DefaultRouteTemplates`; существующим компаниям он добирается сам (см.
   выше), новым — при создании;
4. по желанию — описание для автоопределения типа моделью (`DocumentTypeGuessService`) и подписи в интерфейсе
   (подсказки полей): без них тип работает, просто без подсказок.
Форма проверки, извлечение полей моделью, `RuleEngine`, выбор автора, предпросмотр и движок согласования типа не знают.

## 6. Демо-режим

При `DEMO_MODE=true` кнопка «Открыть демо-компанию» создаёт **личную песочницу
проверяющего**: копию демо-компании с вымышленными участниками — автор, юрист,
бухгалтер, директор, администратор, — документами в разных состояниях и ожидающей
заявкой на вступление. Сам проверяющий её участником **не становится**: он действует
от имени вымышленных участников через `X-Demo-Act-As`, а его реальная компания
и экран приветствия остаются независимыми.

- Каждый проверяющий работает в своей песочнице: чужие действия не ломают ему сценарий.
- `X-Demo-Act-As` принимается только для участников **своей** песочницы.
- «Начать заново» пересоздаёт песочницу.
- Песочницы помечены `is_demo` и не участвуют ни в одной выдаче реальных компаний.

Список разрешённых проверяющих не заводим: учётных записей жюри мы не знаем,
а закрытый демо-режим — прямой риск гейта «невозможно проверить сценарий».

## 7. Фронтенд

```
frontend/src/
├── app/             запуск, маршрутизация экранов, сессия (ответ /me, демо-участник)
├── max/             обёртка над window.WebApp: initData, startParam, шаринг, заглушка для dev
├── api/             клиент: заголовки, разбор ошибок, функции по эндпоинтам
├── screens/         экраны из SCREENS.md, по папке на экран
└── components/base/ свои базовые компоненты, которых нет в MAX UI
```

- **Отдельной библиотеки состояния нет.** Сессия — React-контекст, данные экрана
  загружаются экраном. Для двух недель этого достаточно.
- **Стартовый экран выбирается по `GET /me`**, а не по локальному состоянию.
- **Права на действия приходят с бэкенда** (`permissions`, `myActiveStepIds`),
  фронтенд их не вычисляет.
- Демо-участник хранится в контексте и уходит заголовком `X-Demo-Act-As` в каждом запросе.
- Заглушка `initData` — только в `import.meta.env.DEV`.
