# Экраны мини-приложения

> **Визуальные принципы — [DESIGN-DECISIONS.md](DESIGN-DECISIONS.md), раздел «Интерфейс».**
> Этот файл описывает логику экранов: какие данные, запросы и состояния.

Что на каждом экране, какие действия и состояния. Визуальный стиль — дизайн-система `frontend/src/ui/`
поверх `@maxhub/max-ui`. Данные экранов — в [API_CONTRACTS.md](API_CONTRACTS.md).

## Общие правила для всех экранов

- **Четыре состояния у каждого экрана с данными:** загрузка (скелетон или `Spinner`),
  данные, пусто (текст + следующее действие), ошибка (текст из `message` + «Повторить»).
  Исключение — ошибка конкретного действия (решение по шагу, отправка на маршрут):
  у неё нет своего «Повторить», нажатие на кнопку действия и есть повтор; текст `message`
  просто выводится (`ErrorText`), без второй, ничего не повторяющей кнопки рядом.
- **Главное действие экрана — одна заметная кнопка внизу.** Второстепенные — выше и тише.
- **Ошибки бэкенда показываем его текстом** (`message`), не пишем свои.
- **Кнопки, которых нельзя нажать, не показываем**, а не делаем неактивными — кроме
  случаев, когда нужно объяснить почему (отправка при замечаниях, пустая роль).
- **Статусы различимы не только текстом:** своя метка с цветом и значком у каждого статуса.
- **Главная вместо нижнего меню.** Разделы — плитки главного экрана; нижнего меню нет. На «Компании»
  и плитке «Компания» — счётчик новых заявок для администратора.
- **Назад.** На некорневых экранах над заголовком — ссылка «‹ Документы» / «‹ К документу» /
  «‹ Компания»: системную кнопку MAX замечают не все. Она и системная `WebApp.BackButton`
  (`routes/useMaxBackButton.ts`) ведут в одно место — к логическому родителю экрана
  (`routes/backNavigation.ts`): проверка и маршрут → карточка, карточка и загрузка → список,
  администрирование → «Компания». Переход к родителю **всегда заменяет текущий экран**, а не
  делает шаг назад по истории браузера: в веб-версии MAX у фрейма приложения и страницы MAX общая
  история, и `history.back` отменял переход самого MAX — «‹ Документы» переставала работать
 . Списки и «Компания» ведут на главную, карточка — в тот список, откуда её
  открыли (иначе — на главную). На корневых экранах (главная, приветствие, ожидание решения) системная кнопка скрыта.
- **Повторное открытие из бота.** Кнопка уведомления при уже открытом мини-приложении
  ведёт на нужный документ: запуск отличается по данным запуска, а не по пути
  (`app/launch.ts`), поэтому ссылка отрабатывает на любом экране. Новые данные запуска в адресе
  ловятся по `hashchange`, `popstate`, `pageshow`, `focus` и `visibilitychange`. Как клиент MAX
  передаёт повторное открытие, в документации моста не описано, поэтому сообщения моста пишутся
  в консоль с меткой `[approval]` (уровень debug) — для проверки на конкретном клиенте.
- **Ссылка важнее демонстрации.** Человек без компании, которого приложение вернуло бы в демонстрацию,
  при открытии по ссылке (приглашение, документ) попадает по ссылке.
- **Демо-режим:** в углу — плашка «Демо: действую как <имя>», по нажатию — список
  участников своей песочницы, «Начать заново» и «Выйти из демо». Показывается, когда
  фронтенд работает в песочнице (`/me.actingAs` не пустой).

- **Ширина:** на широком окне (веб-версия MAX) всё приложение — одна колонка 560 px по центру (`.app-frame`,
  `theme/tokens.css`). Отдельной десктопной вёрстки нет.
- **Тексты — коротко.** Подпись — одна строка по делу, без пересказа того, как устроен сервис;
  второстепенный текст — не мельче 13 px.
- **Роли выбираются одним компонентом везде** — на заявке, в участнике, в личной ссылке:
  чипы выбранных ролей с «×» и кнопка «+», открывающая список оставшихся ролей компании.
  «Права администратора» — отдельный переключатель рядом, не чип: это не роль.
- **Тексты замечаний и источники — только из бэкенда** (`message`, `sourceTitle`, `sourceRef`);
  примеры для вёрстки — [RULES.md](RULES.md). Демо-документ — служебная записка.

Статусы, их слова, иконки и цвета — один словарь `frontend/src/ui/status.ts` и токены `ui/tokens.css`:
метка документа, решения людей и таймлайн берут их оттуда. Цвет никогда не единственный признак — рядом
всегда слово и иконка.

## Навигация

```
Запуск → GET /me
 ├─ нет компании, нет заявки ──→ 1. Приветствие
 ├─ есть заявка на рассмотрении ─→ 5. Ожидание решения
 ├─ startParam c_<код> ─────────→ 4. Присоединение (код подставлен)
 ├─ startParam p_<токен> ───────→ 4б. Вступление по личной ссылке (SHOULD)
 ├─ startParam d_<id> ──────────→ 11. Карточка документа (из уведомления бота)
 ├─ startParam s_<запрос> ──────→ Поиск с этим запросом (кнопка бота «Показать все»)
 ├─ startParam a_requests ──────→ 6. Заявки (кнопка бота «Открыть заявки»)
 └─ есть компания ──────────────→ Главная (/home): плитки, поиск 🔍 и «Новый документ»
                                    ├─ «На моём согласовании» ┐
                                    ├─ «Мои документы»         ├ 8. Список раздела → 11. Карточка
                                    ├─ «Общие документы»       ┘
                                    ├─ «Компания» → 8а → администрирование 3, 6, 7; правила; демо
                                    └─ «Новый документ» → 9. Загрузка
```

Песочница не влияет на навигацию: `/me.membership` — только реальная компания.
Демо включается с экрана приветствия или из раздела «Компания» (в том числе участником
реальной компании) и выключается «Выйти из демо».

## Подключение компании

### 1. Приветствие
- Заголовок, строка о сервисе и три коротких пункта: проверка до отправки, понятный маршрут,
  уведомления в MAX (раньше экран был пустым, текст мелким).
- Кнопки закреплены внизу: **«Создать компанию»**, «Посмотреть демонстрацию» (только при `demoMode`, второй —
  чтобы проверяющий не пропустил; одно название и при существующей песочнице, она не пересоздаётся) и
  «Присоединиться по коду». Демонстрация подаётся как знакомство с продуктом, а не как режим работы.
- Человек без компании, который был в демонстрации, при следующем открытии возвращается туда же
  (запоминается в браузере); сотрудник настоящей компании всегда открывает свою компанию.
- Состояний данных нет — экран статичный.

### 2. Создание компании
- Поле «Название компании» — обязательное.
- «Часовой пояс» — выбор из 11 поясов России нижней панелью: «МСК+4», под ним города пояса; сразу
  подставлен по поясу телефона. Выбирается пояс, а не город: города компании может не быть
  в списке. По поясу компания считает «сегодня».
- Поле «ИНН» — необязательное, с подсказкой «не проверяется».
- Кнопка **«Создать»**. Создатель становится администратором и получает роль «Директор».
  После — сразу на 3. Приглашение с подсказкой «Пригласите сотрудников. Пока их нет,
  документы, где согласует директор, будут согласованы вами автоматически — это видно
  в истории».

### 3. Приглашение (администратор)
- Блок «Код компании»: крупно код, под ним ссылка `https://max.ru/t354_hakaton_max_bot?startapp=c_<код>`
  (ссылку и код даёт бэкенд). В коде нет символов 0, 1, O, I, L — в примерах тоже.
- Кнопки: **«Поделиться»** (системный шаринг MAX), «Скопировать код».
- Ниже — «Перевыпустить код» с подтверждением: «Старый код перестанет работать.
  Уже поданные заявки останутся».
- Пока в компании только администратор (сразу после создания) — закреплённая «Готово» → главная.
- *SHOULD.* Блок «Личные приглашения»: кнопка «Создать личную ссылку» → выбор ролей
  (тот же компонент ролей, без прав администратора) → предупреждение «Вступит тот, кто откроет
  первым. Отправляйте только в личные сообщения» → ссылка и «Поделиться». Неиспользованные ссылки — строками
  «роли · срок»; по нажатию — лист с «Поделиться» и «Отозвать ссылку».

### 4. Присоединение по коду
- Поле кода (8 символов, заглавные, без пробелов).
- **По ссылке с кодом** код проверяется и заявка подаётся сама, без нажатий → 5 «Заявка отправлена»; если
  проверка или отправка не удались — ошибка и ручной повтор.
- Вручную: после ввода — название компании «Вы вступаете в компанию «Ромашка»» (название с кавычками — как есть, без кавычек в кавычках) и кнопка **«Отправить заявку»** → 5.
- Ошибки: «Код не найден», «Слишком много попыток, попробуйте через час».

### 4б. Вступление по личной ссылке — SHOULD
- Компания и список ролей, которые получит человек.
- Кнопка **«Вступить»** — без неё ничего не происходит; **«Не сейчас»** → приветствие.
- Ссылка использована, просрочена или отозвана — объяснение и кнопки «Присоединиться по коду» и «На главную».

### 5. Ожидание решения
- «Заявка в компанию «<компания>» ждёт решения администратора. Мы сообщим в чате, когда администратор её рассмотрит».
- Кнопка «Отменить заявку» с подтверждением.
- При повторном открытии приложения — снова этот экран, пока заявка не решена.

### 6. Заявки (администратор)
- Список: имя, когда подана. Вернувшийся сотрудник (исключён раньше) — с отмеченными прежними ролями и строкой
  «Возвращается в компанию — отмечены прежние роли: …»: администратору остаётся «Принять».
- В строке заявки — выбор ролей (общий компонент: чипы и «+»), отдельный переключатель «Права
  администратора» и две кнопки: **«Принять»** и «Отклонить». «Принять» неактивна,
  пока не выбрана хотя бы одна роль.
- Пусто: «Новых заявок нет» и почему так бывает после сообщения бота: заявку уже рассмотрел другой администратор
  или отозвал сам сотрудник.

### 7. Участники (администратор)
- Список: имя, роли метками, отметка «Администратор».
- Нажатие — выбор ролей (тот же компонент) и отдельный переключатель «Права администратора», «Сохранить».
  Права администратора — не роль: в маршрутах они не участвуют.
- Ошибки показываются текстом бэкенда: «Нельзя снять права администратора с последнего администратора».
- «Исключить из компании» — сразу, с подтверждением: «Документы, которые ждут решения сотрудника, вернутся авторам».
  Под выбором ролей, когда роль снимается, — та же оговорка для снятой роли (раньше исключить
  человека с незавершёнными согласованиями было нельзя). После сохранения или исключения сообщение называет, сколько
  документов вернулось авторам: «2 документа вернулись авторам — их можно отправить заново».
- Исключённые — не в общем списке, а свёрнутым блоком «Исключённые · N» внизу: запись остаётся ради истории
  решений, вернувшийся по коду или ссылке человек занимает прежнее место.

## Документы

### Главная
- Заголовок — название компании, под ним «кто вы» (имя и роли).
- Плитки 2×2: **«На моём согласовании»** (ждут вашего решения, счётчик — акцентный), **«Мои документы»**
  (созданные вами, включая черновики; счётчик — сколько вернули на доработку), **«Общие документы»** (с вашим
  решением и открытые всем), **«Компания»**
  (счётчик заявок у администратора). Названия одни и те же на плитках, в заголовках списков и в текстах бота
  (`DOCUMENT_LISTS` в `routes/paths.ts`).
- Справа от названия — 🔍 «Поиск документов» → поиск по всем разделам.
- Под плитками — «Ждут вас»: документы на вашем решении и ваши возвращённые; если ждать нечего — «Недавние
  документы» (ваши три последних).
- Длинное название компании (больше 40 символов) — на ступень мельче, целиком.
- Закреплённое главное действие — «Новый документ». Плитки помещаются без прокрутки на 360×640.

### Поиск документов
- Поле поиска: название, автор или номер; запрос — в адресе (`?q=`), «назад» с карточки возвращает к результатам.
- Результаты — группами по разделам: «На моём согласовании», «Мои документы», «Общие документы»; документ — в первом
  разделе, где нашёлся. Больше 20 в разделе — «Показаны первые 20 из N — уточните запрос».

### 8. Список раздела
- Шапка: «‹ Главная», название раздела и пояснение.
- Поле поиска вверху: название, автор или номер; запрос уходит через паузу в наборе.
- Два чипа: **статус** («Все статусы ▾» — выбор в нижней панели, выбранный статус виден на чипе) и «Фильтры» (вид,
  автор, когда создан — «Когда угодно / За 7 дней / За 30 дней / За 3 месяца / За год»). Ряда из семи чипов статусов
  нет — он не помещался в ширину; нативных полей даты нет — их формат зависит от языка браузера. В выборе
  вида «Другой документ» — отдельной группой «Вне шаблонов» («Все вне шаблонов»).
- По 30 документов; дальше — «Показаны N из M» и «Показать ещё». Если список сдвинулся (документ обновился и поднялся
  наверх), загруженные страницы перечитываются с начала. Бывшие сотрудники появляются в фильтре «Автор», когда их
  документ уже загружен в список, — активные коллеги есть там сразу.
- Строка: название на всю ширину, под ним метка статуса и «вид · автор · дата»; в «На моём согласовании» —
  «пришёл сегодня», «пришёл вчера» или «ждёт N дней» (календарные дни в поясе компании) вместо метки. У «Другого документа» вместо «Другой документ» — вид, как его назвал документ, с ✦,
  если его нашёл ИИ: «Договор аренды ✦».
- Пусто — что здесь появится и почему; при фильтрах или поиске — «Ничего не нашлось» и «Сбросить поиск и фильтры».
- В «Мои документы» закреплена кнопка «Новый документ».

### 8а. Компания
- Название компании, под ним «Часовой пояс МСК+3» (в демо — «Демонстрационная компания с вымышленными
  сотрудниками»).
- «Сотрудники · N» — всем участникам (`GET /orgs/current/colleagues`): имя и роли; администратору — «Управлять».
- Администратору — «Пригласить сотрудников», «Заявки на вступление» (со счётчиком), «Участники и роли», «Название
  компании» (нижняя панель с полем) и «Часовой пояс» (выбор нижней панелью) — оба вне демо. В «Участниках»
  администратор открывает и себя, но у себя меняет только роли.
- «Правила проверки» → 8б — всем участникам; подпись у администратора «…и настройка под компанию».
- «Кто согласует документы» (`GET /orgs/current/routes`): пояснение «так маршрут заполняется сам, когда вы
  отправляете документ…», легенда замка, для каждого вида — этапы по строкам «1. Юрист и Бухгалтер — одновременно»,
  «2. Директор 🔒». Администратору нажатие на вид (в том числе «Другой документ»: по умолчанию обязательных там нет, но их
  можно отметить) открывает отдельный экран → 8в «Маршрут — <вид>».
- «Показатели согласования» (переехали со списка документов): сколько обычно проходит от отправки до
  «Согласован» и какую долю документов возвращали; меньше часа — словами.
- «Как устроено согласование» — пять шагов без названия модели: подготовка, исправление, маршрут, решения,
  результат.
- При `demoMode` внизу — «Демонстрационный режим»: вне демо «Посмотреть демонстрацию» (одно название — и в первый раз, и потом), внутри —
  «Выйти из демонстрации» и «Начать заново» (с подтверждением: демо-компания станет как в начале).

### 8б. Правила проверки
Кто сюда приходит: автор или согласующий — понять, откуда замечание; администратор — подстроить типовые
правила под документы компании.
- Подпись: администратору «Типовые правила сервиса. Нажмите на правило, чтобы подстроить его…», остальным —
  «…Менять их может администратор». Если что-то настроено — «Изменено компанией: N».
- У правила «не позже сегодняшнего дня» в панели — «„Сегодня“ — по времени компании: Омск, МСК+3».
- «Вид документа» — выбор (как на загрузке, «Другой документ» последним).
- Карточка правила: **что проверяется словами** («Кому» заполнено, «Текст» — не короче 50 символов, «Вид отпуска» —
  одно из: …), важность меткой («Критично» / «Предупреждение» / «Совет», или «Не проверяется»), текст замечания,
  основание одной строкой — без пояснения в скобках («Правило компании: ГОСТ Р 7.0.97-2016 «…», п. 5.15»;
  название, которое ввела компания, не сокращается;
  у рекомендации сервиса — просто «Рекомендация сервиса»), метки «🔒 Закон — не меняется» и «Изменено компанией».
  Порядок — по полям документа, внутри поля — сначала «заполнено».
- Администратор нажимает на правило → шторка: «Проверять это правило»; важность с пояснением («Документ нельзя
  отправить, пока не исправят» / «Замечание видно, отправить можно» / «Мягкая подсказка»); «Не короче, символов» или
  «Допустимые значения — по одному в строке» (только у этих проверок); «Текст замечания — его увидит автор»;
  «Основание — документ компании» и пункт; «Сохранить», «Сбросить к типовому» (если изменено). Подпись: действует
  для новых проверок, черновики — после «Проверить заново», документы на согласовании не меняются.
- У закона вместо формы — «Требование закона одинаково для всех компаний — выключить или ослабить его нельзя».
- Остальным участникам карточки не нажимаются.
- Внизу: «Новые правила и поля добавляются в шаблон сервиса, а не здесь».
- Ссылка `/company/rules?rule=<id>` сразу выбирает вид документа и, у администратора, открывает правило.

### 8в. Маршрут — редактор шаблона
Только администратор, только вид с шаблоном (не «Другой документ» — у него шаблона нет). Отдельный экран
`/company/routes/:typeId`, а не панель поверх «Компании»: содержимого достаточно, чтобы над
панелью открывались ещё панели, а «Сохранить» уезжало вниз со списком.
- Шапка: «‹ Компания», «Маршрут — <вид>», подпись «Действует на новые отправки» — короче, чем в MVP-версии панели:
  что обязательную роль можно убрать, и так видно по замку рядом с ролью.
- Этапы — карточки «Этап N · одновременно» (двое и больше параллельно) или «· Утверждение» (последний этап из одной
  роли — та же подпись, что у автора видит в своём конструкторе); у этапа больше одного — «⋯»
  (порядок этапа: «Поставить раньше/позже»).
- Роль в этапе: имя, замок и подпись «Обязательна — автор не убирает» или «Не обязательна»; нет носителей —
  «сейчас ни у кого нет этой роли». Нажатие — шторка «роль»: сделать обязательной/необязательной (с подтверждением,
  если носителей нет — тот же диалог, что в), перенести в любой этап или отдельным новым, убрать из маршрута.
  **В отличие от конструктора маршрута документа: администратор убирает и переставляет любую роль, включая
  обязательные** — замка, который не даёт убрать, здесь нет: запрет действует только на автора при отправке.
- «+ Роль» у каждого этапа и «+ Новый этап» внизу — список ролей компании, которых ещё нет в шаблоне (панель поиска
  при большом списке).
- Пусто (все роли убрали) — «Нужна хотя бы одна роль — иначе шаблон не сохранится»; «Сохранить» неактивна: пустой
  шаблон неотличим от «ещё не создан» и был бы молча восстановлен по умолчанию.
- Закреплённая **«Сохранить»** — неактивна, пока нет изменений или список пуст.
- «‹ Компания» с несохранёнными изменениями — подтверждение «Выйти без сохранения?».

### 9. Новый документ — шаг 1 «Файл»
- Под шапкой — шаги создания: **1. Файл → 2. Проверка → 3. Маршрут** (тот же индикатор на экранах 10 и 12).
- Зона загрузки на всю ширину: пунктирная карточка, значок, «Выберите файл документа»; под ней строка «PDF или DOCX ·
  до 10 МБ». В правом верхнем углу — «?» (значок ~20 px, зона нажатия 44×44) → нижняя панель «Какие файлы
  подходят»: по строке на PDF с текстом, PDF-скан, DOCX и «DOC — не подходит, сохраните как DOCX», по коду.
- `accept` — только PDF и DOCX. Файл проверяется сразу после выбора: не тот формат, пустой, больше 10 МБ —
  красная обводка и текст **в зоне** («Фото не подходит. Загрузите PDF или DOCX…»; на DOC — «устаревший формат Word… сохраните как DOCX»).
- После выбора — карточка файла: имя, размер, «Заменить», «Убрать». Если следующий выбранный файл не подошёл, прежний
  остаётся, а ошибка — под ним.
- Под зоной — «Приложения»: список выбранных (имя, размер, «Убрать») и «+ Приложение»; можно выбрать сразу
  несколько. PDF, DOCX, XLSX, PNG, JPG, до 10 файлов по 10 МБ; не подошедший или уже добавленный файл не добавляется,
  ошибка с его именем — под списком. Все файлы вместе больше 30 МБ — строка у кнопки «Далее», кнопка неактивна (размеры
  известны до отправки). Ошибки сервера — там же. Во время отправки файлы не меняются.
- Пока нет ни файла, ни приложений — «Нет файла? Служебную записку можно заполнить прямо здесь» → 9а.
- «Вид документа» — нижней панелью, по умолчанию «Определить автоматически»; под ним — что будет проверено.
- Название (необязательно), «Кто видит документ», «Содержит чувствительные данные» (тогда вид выбирается вручную и
  ниже появляются поля).
- Закреплено: **«Далее: проверить документ»**; во время запроса — «Распознаём и проверяем документ — до минуты».
- После — 10. Результат проверки.

### 9а. Служебная записка в приложении — SHOULD
- Документ-форма без файла, подпись одной строкой: «Файл не нужен: правила проверят записку сразу».
- Поля типа «Служебная записка» по порядку схемы: кому, от кого (по умолчанию — имя текущего пользователя), дата
  (по умолчанию сегодня), номер, заголовок, текст (многострочный), должность и расшифровка подписи.
- Название — необязательное: «возьмём заголовок записки». Видимость — как на 9.
- Кнопка **«Проверить»**: без распознавания, правила проверяют поля сразу → 10.
- Нет типа в справочнике — «Служебные записки в компании не настроены. Загрузите документ файлом».

### 10. Результат проверки — шаг 2 «Проверка»
- Пока автор готовит документ к первой отправке — индикатор шагов (шаг 2), и когда критичные замечания ещё мешают.
- Документ вернули и он ещё не отправлен заново — сверху комментарий вернувшего, как на карточке.
- Поля с замечаниями: при чтении — значок цвета важности у подписи, при правке — рамка того же цвета и текст замечания
  под полем вместо примера.
- Под заголовком: вид (✦, если его выбрал ИИ) и версия; автору черновика — «Сменить вид» (документ проверяется
  заново по правилам выбранного вида).
- **«Другой документ»:** вместо строки вида — плашка «ИИ распознал: Договор аренды ✦. Такого вида нет в
  шаблонах компании — проверим общие реквизиты: дату, номер, заголовок и подпись. Согласующих выберете сами» и кнопка
  «Выбрать вид из списка» (та же панель, что «Сменить вид»). Вид не распознан — «Вид документа не распознан».
- «Как проверялся документ» (свёрнуто, раскрыто без модели): ИИ (GigaChat) нашёл поля в тексте,
  правила проверили их, решение принимают люди. Без модели — почему поля не заполнились сами.
  Файл без текста (скан, фото): «В файле нет текста — похоже, это скан…», поля вручную (`check.textMissing`).
- Блок «Замечания»: сначала критичные, потом предупреждения и подсказки. Каждое: важность
  меткой, текст, поле, источник правила с видом — тем же словарём, что в «Правилах проверки»: «Закон», «Правило компании»,
  «Рекомендация сервиса»
  и ссылкой, цитата из документа и страница, если есть.
- Нет замечаний: «Замечаний нет» — явно, а не пустой блок.
- У черновика и возвращённого документа рядом с заголовком «Замечания» — **«Проверить заново»**: по текущим
  правилам компании, по тем же полям, без повторного чтения файла. Нужна, когда администратор поменял правила после
  проверки. У возвращённого проверяется новая версия-черновик с теми же файлами и полями.
- Администратору у основания каждого замечания — «Настроить правило» → 8б с открытым правилом. Важность «Совет»
  (а не «Подсказка») — те же слова, что в «Правилах проверки».
- Проверка не выполнилась (`check.status = FAILED`): «Проверка не выполнена». Отправка недоступна.
- Блок «Данные документа»: рядом с заголовком ✦ — нажатие открывает «✦ — значение от ИИ» (что это и что ИИ ничего
  не решает); под заголовком строка «✦ — заполнено ИИ, проверьте»; ✦ — у каждого значения, найденного ИИ.
  У каждого поля — откуда значение: «Из текста документа: «цитата»»,
  «Указано вручную» или «Изменено вручную, файл не менялся. В файле: «…»» (виден и согласующему).
  **Одна** кнопка правки — «Изменить» у этого блока; когда есть критичные замечания или документ
  возвращён, она главная (синяя). Внизу экрана кнопки правки полей нет.
- Форма правки:
  - DOCX (`canCorrectFile`): **«Исправить и проверить»** — значения вписываются в сам
    файл на место прежних, с тем же оформлением; новая версия проверяется заново. Изменённым
    считается поле, которое отличается от **того, что в файле** (`fileValue ?? value`). Пустое значение
    не вписывается (иначе вырезало бы текст), поле, которого в файле нет, — сразу с объяснением.
    Что вписать не удалось — списком с причиной, а введённые значения остаются в форме. Проверка
    новой версии не выполнилась — сообщение об этом, а не «проверена заново». Второстепенно:
    «Сохранить, не меняя файл» — ИИ прочитал поле неверно или поля нет в файле.
  - PDF: «Сохранить и проверить» с пояснением, что сам PDF так не исправить, и «Заменить файл».
  - `RETURNED`: та же форма. Возвращённая версия не меняется, поэтому сохранение сначала создаёт
    новую версию с теми же файлами — документ становится черновиком.
- **Каждое действие — в одном месте.** Вверху, рядом с типом и версией: «Сменить тип» (черновик) и «Заменить
  файл» (черновик и `RETURNED`, в том числе у черновика без замечаний). «Заменить файл», а не «Другой файл»: это
  новый файл того же документа (п. 8). Внизу — только куда дальше: **«Далее: выбрать согласующих»** → 12 и «Сохранить черновик»
  (ведёт на карточку с сообщением «Черновик сохранён»); при критичных замечаниях — только «Сохранить черновик».
  Во время правки полей «Сменить тип» и «Заменить файл» скрыты.
- **Документ-форма (`versions[].content`)**: «Сменить тип» и «Заменить файл» нет; «Как проверялся документ» —
  «Записка заполнена в приложении — правила проверили её поля» (свёрнуто). «Изменить» правит саму записку, в том
  числе у `RETURNED`: сохранение создаёт новую версию формы целиком (не «с теми же файлами»).

### 10а. Замена файла
- Текущий основной файл, выбор нового («Новый файл»), «Содержит чувствительные данные».
- «Приложения» — тот же список, что на 9: у приложения прежней версии «Убрать» (имя зачёркивается, «Не войдёт
  в новую версию», кнопка становится «Оставить»), новые — с пометкой «новое» и «Убрать», «+ Приложение». Нативных
  checkbox нет. Оставленные уходят в `keepFileIds`, новые — в `attachments`. 30 МБ на версию (основной файл,
  оставленные и новые приложения) и ошибки сервера — у кнопки, как на 9.
- **Без нового файла** версия переносит поля прежней, в том числе ручные правки, и перепроверяет их
  правилами без модели (файл не изменился). Кнопка «Загрузить и проверить» доступна, если выбран
  новый файл, изменился набор приложений, включены чувствительные данные (поля вводятся здесь же)
  или документ возвращён — тогда так переходят к правке полей, не меняя файл.
- Подсказка под выбором файла — только формат и размер: поля правятся на экране проверки.

### 11. Карточка документа
- Шапка: «‹ <список, откуда пришли>» (или «‹ Главная»), название, под ним метка показываемого статуса (`displayStatus`)
  и «вид · автор · версия». У «Другого документа» — распознанный вид с ✦ и приглушённая пометка «вне шаблонов»:
  нажатие — нижняя панель (вид распознал ИИ, в шаблонах его нет, проверялись только общие реквизиты, маршрут
  составлял автор).
- Плашки над таймлайном: причина возврата с комментарием, «отозван автором», «вернулся автоматически» (выбыл согласующий).
- **«Где документ сейчас» — таймлайн:** «Создан» → этапы → «Утверждение» → итог («Утверждён» / «Согласован» /
  «Отклонён» / «Возвращён на доработку»). Пройденный шаг — заполненная точка и сплошная линия, текущий — крупнее,
  «Сейчас здесь», будущий — серая точка и пунктир. В этапе — люди с решением словом и значком, временем и комментарием;
  у будущих этапов решений нет. Два и больше пройденных этапа сворачиваются в «Этапы 1–N пройдены · Показать».
- Ниже: изменения с прошлой версии; если есть сводка — блок **«Кратко от ИИ»** (✦, пояснение по нажатию) над
  файлами; содержание записки-формы или файлы (нажатие — скачать), «Замечания проверки» со счётчиком (→ экран 10),
  решения по прошлым версиям, версии. Сводки нет — блока нет (у формы её нет никогда: модель её не читает).
- **Закреплённые действия:** у согласующего — «Согласовать» (у утверждающего — «Утвердить») на всю ширину, ниже поровну
  «Вернуть на доработку» и тихая «Отклонить»; обе открывают нижнюю панель с обязательным комментарием, «Отклонить» —
  ещё и подтверждение. У автора: «Отозвать с согласования»; у черновика — «Далее: выбрать согласующих» или «Исправить
  замечания»; у возвращённого — «Исправить документ» и «Отправить заново без изменений». У утверждённого или
  согласованного документа с файлом — «Скачать итоговый файл»; у записки, заполненной в приложении, файла нет —
  её текст на карточке, закреплённого действия нет (выгрузка в файл — WON'T). Ошибка скачивания — над действиями экрана.
- **В демонстрации**, когда ход не за текущим участником, — главная кнопка «Действовать как <тот, чья очередь>»:
  переключает участника и оставляет на карточке.
- **«Удалить черновик»** — в конце карточки тихой кнопкой, только у черновика, который ни разу не
  отправлялся; подтверждение «Удалить черновик?» → «Мои документы» с сообщением «Черновик удалён».

### 12. Маршрут — конструктор
- Пришли с экрана проверки — индикатор шагов (шаг 3 «Маршрут»); закреплено «Отправить на согласование».
- Обязательная роль есть только у автора — строка «Вы · Директор — согласуется автоматически» отдельным этапом после
  согласующих, перед «Утверждением» (там же её ставит сервер). Утверждающий по умолчанию — последний этап шаблона,
  если в нём один человек и это не автор.
- Пустой маршрут, без которого не отправить (`needsApprover`), — карточка «Этап 1» с «+ Согласующий». Если маршрут и так
  проходит (есть утверждающий или шаг автора) — вместо неё пунктирная зона «+ Согласующий»: добавить можно, не нужно,
  и нумерация этапов не сбивается (было два «Этапа 1»). «Отправить» неактивна с подсказкой, пока пуст маршрут
  (когда согласовать есть кому) или нет обязательной роли — те же проверки, что на сервере.
- Подсказка о перетаскивании — только когда в маршруте есть люди.
- Этапы — карточки «Этап N · одновременно» с людьми (имя, роль); у каждого — ручка ⋮⋮ (перетащить), нажатие — меню
  «перенести в этап / отдельным этапом / сделать утверждающим / убрать», справа — «×» или замок (обязательный: убрать
  нельзя). У этапа — «+ Согласующий» и «⋯» (раньше/позже). Под этапами — пунктирная заглушка «+ Новый этап», на неё
  же можно бросить человека.
- Блок «Утверждение» — последний, один утверждающий; сменить — перетащить или «Сделать утверждающим» (прежний, если
  обязательный, становится последним этапом). Пусто — итог «Согласован».
- Выбор сотрудника — нижняя панель с поиском; уже стоящие в маршруте неактивны с подписью «уже в маршруте, этап N».
- Роль с несколькими кандидатами — место «Юрист: выберите сотрудника»; пока не выбран, «Отправить» неактивна с подсказкой.
- Предзаполнение — маршрутом прошлой версии, иначе шаблоном вида документа. Логика — `routeBuilder.ts` с тестами.
