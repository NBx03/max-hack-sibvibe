### Ловушки, уже проверенные вручную — чтобы не наступить повторно

- **`spring-ai-bom:1.1.2` в `dependencyManagement` обязателен.** Стартер GigaChat
  объявляет `spring-ai-autoconfigure-*` без версий; без BOM сборка не резолвится.
- **React строго 19.2.8.** В README библиотеки написано «React 18+» — это неверно,
  `peerDependencies` требуют точную 19.2.8.
- **Spring Boot 3.5 в OSS EOL с 30.06.2026.** Выбран сознательно: под срок в две
  недели стабильность экосистемы важнее свежести, а экосистема Boot 4 / Spring AI 2 менее устоялась. Версии
  запинены, решение объяснено в презентации как осознанное. Миграция на Boot 4.1
  — план после пилота.
- **MAX Bridge не npm-пакет.** Это `window.WebApp`, подключается скриптом в
  `index.html` — `https://st.max.ru/js/max-web-app.js`, сверено с
  dev.max.ru/docs/webapps/bridge (2026-09-19). Библиотека инициализируется сама
  при загрузке страницы, отдельного `ready` не требует. `initData` — подписанная,
  но не зашифрованная строка; фронтенд её не разбирает, а целиком пересылает
  на бэкенд — разбирает и проверяет подпись только `MaxIdentityVerifier`.
- **В MAX Bridge нет выбора или съёмки файла.** Сверено с
  dev.max.ru/docs/webapps/bridge (2026-09-23): из файловых методов есть только
  `openCodeReader(fileSelect)` — это сканер QR-кода с опциональным выбором файла
  для распознавания, а не общий file picker или камера. Поэтому загрузка документа
  остаётся обычным `<input type=file>` (зона загрузки `ui/FileDrop.tsx`) и внутри MAX, и вне его —
  отдельного метода моста ждать не от чего. `downloadFile(url, fileName)` — то же
  сверено, реальный метод моста, уже используется (`max/webApp.ts`, карточка документа).
- **Кнопки уведомлений бота — тип `open_app`, не `link`.**
  Схема github.com/max-messenger/api-schema (сверено 2026-09-23): у `OpenAppButton`
  поля `web_app` (ник бота) и `payload` (до 512 символов, `^[\w-]*$` — наш формат
  `startapp`-payload вписывается без изменений); по нажатию мини-приложение
  открывается сразу, без прыжка на страницу max.ru. `MaxBotApiNotifier` разбирает
  готовый URL от `InviteLinks` обратно на `web_app`+`payload` — отдельной копии
  константы с ником бота в модуле `bot` нет.
- **Образы MinIO живут на quay.io, не на Docker Hub.** `minio/minio` на Docker Hub
  больше не существует, `docker pull` падает с «repository does not exist».
  Правильные координаты — `quay.io/minio/minio` и `quay.io/minio/mc`.
- **Бота создали организаторы, ник не наш.** Наш бот — `@t354_hakaton_max_bot`
  («Хакатон МАХ 354»), проверено запросом `GET /me` с токеном. Ссылка на
  мини-приложение: `https://max.ru/t354_hakaton_max_bot?startapp=<payload>`.
  Токен — только в локальном `.env` и на стенде, никогда в репозитории и задачах.
- **Bot API: токен только в заголовке `Authorization`.** Передача токена параметром
  `access_token` отключена — сервер отвечает 401 «deprecated».
- **Адрес Bot API — `platform-api2.max.ru`** (официальный с 19.07.2026). У него, как и у
  GigaChat, сертификат удостоверяющего центра Минцифры («Russian Trusted Root CA»),
  которого нет в стандартном хранилище Java. **Корень встроен в образ бэкенда**:
  `backend/certs/russian_trusted_root_ca.pem`, импорт в `backend/Dockerfile`, отпечаток
  проверен. Поэтому `unsafe-ssl` в настройках GigaChat не включаем, проверку сертификатов
  не отключаем. Запуск бэкенда из IDE без Docker — см. DEVELOPMENT.md.
- **Адрес мини-приложения регистрируют организаторы** — через их форму сбора ссылок
  (капитан, email, команда, ссылка). Поэтому: внутри MAX мини-приложение открывается
  **только** по тому адресу, что мы отправили в форму; адрес должен быть **постоянным**
  (свой домен, а не случайный адрес туннеля); отправить его нужно как можно раньше —
  до этого проверить приложение внутри MAX нельзя никому. Локальная разработка —
  в обычном браузере с заглушкой, проверка в MAX — только на стенде.
- **Apache POI не используем.** С транзитивными зависимостями ~17 МБ загрузки
  в каждой холодной сборке; с ним сборка временами уходила за лимит.
  DOCX читается средствами JDK: это zip-архив с `word/document.xml`.
- **Ссылка на мини-приложение с параметром:** `https://max.ru/<бот>?startapp=<payload>`,
  payload до 512 символов, только `A-Z a-z 0-9 _ -`. Во фронтенде —
  `window.WebApp.initDataUnsafe.start_param`, но доверять можно только значению
  из **проверенной** `initData`. Шаринг ссылок: iOS, Android, веб; десктоп — в разработке.
- **Long polling у MAX Bot API официально не годится для продакшена**, а вместе
  с webhook не работает. Локально — polling, на стенде сдачи — webhook, то есть
  публичный входящий эндпоинт для бота всё-таки нужен.
- **`dependency:resolve`, а не `go-offline`** в Dockerfile бэкенда: замерено на
  этом проекте, на одном из замеров после изменения выдало 162 с против 238 с до изменения при лимите 300 с.

## Принятые архитектурные решения

### Маршрутизация согласования: шаблон предзаполняет, автор составляет, обязательные не удаляются

Прежний инвариант
«маршрут только расширяется» **отменён**.

**1. Шаблон маршрута** — задан для пары «вид документа + организация», владеет им организация. Он **только
предзаполняет** маршрут. Строки `ApprovalRoute` группируются по `stage_order`:

```
stage_order=1, role=ЮРИСТ       ┐ параллельный этап
stage_order=1, role=БУХГАЛТЕР   ┘
stage_order=2, role=ДИРЕКТОР      следующий этап, только после первого
```

Одинаковый `stage_order` = параллельно, разный = последовательно. Признак `is_mandatory` у роли в шаблоне — решение
компании: **обязательную роль нельзя удалить из маршрута** (в интерфейсе — замок). Сейчас он задаётся данными по
умолчанию — обязателен только Директор у четырёх видов, у «Другого документа» по умолчанию обязательных нет;
настройка администратором —  и редактор шаблона, в том числе у «Другого документа»:
так в обход обязательных не уйти ни выбором «Другого документа», ни сканом, который тоже становится «Другим
документом». Если вид, выбранный автором, расходится с тем, что определил ИИ (`document.ai_type_id`), автор видит
подсказку со сменой вида, согласующие — строку «Вид выбран автором · ИИ определил: …»; ничего не блокируется.

**2. Резолюция ролей в людей** — при предзаполнении и при отправке:
- 0 носителей у **необязательной** роли → она пропускается;
- 0 носителей у обязательной, но роль есть у автора → шаг сразу согласован с отметкой `AUTHOR_HOLDS_ROLE`
  (проверка №10 ниже);
- 0 носителей у обязательной и ни у кого → отправка блокируется с внятной ошибкой `ROUTE_ROLE_EMPTY`;
- 1 носитель → подставляется; \>1 → **автор выбирает человека** из носителей.

**3. Конструктор автора** — автор двигает **любых** согласующих, включая шаблонных и обязательных: между этапами,
порядок этапов, новый этап в любом месте, блок «Утверждение». Добавляет кого угодно из активных участников с ролью.
Убирает всех, **кроме обязательных**. Добавленные помечаются `origin=ADDED_BY_AUTHOR`.

> **Инвариант: обязательные участники не удаляются; порядок и состав остального — на усмотрение автора.**
> Сервер при отправке проверяет только: все обязательные роли на месте (роль закрыта, если в маршруте есть её
> носитель), **один человек — один раз**, нет пустых этапов. Элемент маршрута — человек, а не пара «роль + человек»
>.

**4. Утверждение.** Последний блок маршрута — «Утверждение», ровно один утверждающий (гриф «УТВЕРЖДАЮ»). По
умолчанию — последний этап шаблона, если в нём один человек; автор может сменить. Кнопка «Утвердить»; пока документ у
утверждающего — «На утверждении», итог — «Утверждён». Без этапа утверждения итог — «Согласован». Слова «подпись» и
«подписать» не используем.

**Семантика этапа:**
- Этап завершён, когда **все его участники** одобрили (AND): шаг, который создан, обязателен для закрытия этапа
  независимо от `is_mandatory`. Кворум «M из N» — сознательно не в MVP.
- «Вернуть» или «отклонить» — **fail-fast**: висящие шаги этапа получают `SKIPPED`, а не удаляются. История
  остаётся честной.
- Возврат → правка → повторная отправка стартует с первого этапа: документ изменился, прежние одобрения относились
  к другой версии. Маршрут прошлой версии **предзаполняет** конструктор, решения сбрасываются.
  **Исключение:** если новая версия ничем не отличается от прошлой — те же файлы и те же поля, —
  одобрения прошлой версии переносятся (`CARRIED_OVER`): это те же байты. Чтобы повторное согласование изменённого
  документа было быстрым, карточка показывает разницу с прошлой версией.

**Конструктор маршрута** — обязательный экран перед отправкой: автор видит полностью разрешённую цепочку с именами.
На карточке документа тот же маршрут показан **таймлайном отслеживания**. Это ответ на «никто не поймёт, где
начало и конец цепочки».

### Решения A–E

- **A. Проверка сценария одним человеком.** `DEMO_MODE=true` добавляет на экран
  приветствия кнопку «Открыть демо-компанию» — она создаёт **личную песочницу
  проверяющего** (копию демо-компании) — и переключатель «действовать как…»
  между её участниками. Каждый проверяющий работает в своей копии, чужие действия
  ему сценарий не ломают. Защита от ситуации, когда основной сценарий нельзя проверить. В демо-компании заранее лежит
  заявка на вступление от вымышленного сотрудника — так проверяющий в одиночку
  может пройти и одобрение заявки с назначением ролей. В проде выключен.
  Следствие: у участника **несколько ролей**, не одна.
- **B. Два уровня поддержки документов.** Хранить, версионировать и проводить
  по маршруту можно **любой документ**. Поддержанный тип получает подробную схему полей
  и правила. **Любой другой** — тип «Другой документ» (`GENERIC`): ИИ находит общие
  реквизиты (вид, дата, номер, заголовок, подпись), правила дают только предупреждения,
  отправке ничто не мешает. По умолчанию при загрузке тип **определяет ИИ** по тексту
  (порт `DocumentClassifier`); не уверен — «Другой документ». Вид, который ИИ распознал у «Другого
  документа» («Договор аренды»), показывается главным с иконкой ИИ ✦, «вне шаблонов» — второстепенной
  пометкой; название документа им не подменяется. Так ИИ работает с любым
  загруженным файлом, а не только с угаданным типом (раньше «Любой файл»
  был без схемы и без ИИ, и проверяющий со своим файлом ИИ не видел вовсе). Объём работ
  по правилам по-прежнему ограничен несколькими типами.
  Демо: **служебная записка** — глубоко, 8–10 правил; **заявление на отпуск** —
  4–5 правил; **заявка на меру поддержки** — 5–6 (решение по); **заявка на командировку** —
  6 правил, все `INTERNAL_POLICY`/`PRODUCT_RULE`: добавлена одной миграцией справочника и записью маршрута по
  умолчанию, без нового кода, — так расширяемость видна на деле (ARCHITECTURE.md, раздел 5).
  Заявка на меру поддержки адресована наружу:
  у неё цена ошибки максимальна, и только у неё есть правила вида `LEGAL`,
  тогда как у остальных — `INTERNAL_POLICY`. Это делает различие видов
  правил демонстрируемым, а не теоретическим. **`LEGAL` — только если закон сам
  определяет проверяемое требование**, а не лишь объясняет, зачем оно нужно:
  иначе продукт заявит правовое основание, которого нет. Подробно — docs/RULES.md.
  **Никакой интеграции с ведомствами нет и не имитируется:** после статуса
  «Согласован» автор подаёт документ сам тем каналом, что есть сегодня.
- **C. Собственный API не заявляем.** Наш REST — внутренний для мини-аппа.
  Кейс, раздел «Формат сдачи»: `openapi.yaml` и `DATA-API.yaml` нужны **только
  решениям с собственным API**, в обязательном для всех списке их нет. И это не
  просто лишняя работа: `DATA-API.yaml` — перечень проверок, которые платформа
  оценки выполняет **автоматически** (базовый адрес, методы, пути, роли тестовых
  учётных записей, ожидаемые коды). Наши эндпоинты требуют подписанных данных
  запуска MAX, заголовок `Dev` живёт только в профиле `dev`, которого на стенде
  нет, — робот получил бы 401 на каждый запрос, и это выглядело бы как
  неработающее решение. Поэтому API не заявляем, `openapi.yaml` и `DATA-API.yaml`
  не готовим. `springdoc` подключён только для внутренней работы команды.
- **D. Spring Boot 3.5.16 + Spring AI 1.1.2.** Обоснование выше.
- **E. Деградация ИИ обязательна.** Недоступность GigaChat не должна ломать
  сценарий — см. README, раздел 12.

### Правки документов

- **Редактора файлов в мини-приложении нет и не будет в MVP.** Править DOCX или PDF
  в браузере на телефоне — это отдельный продукт; встраивание готовых редакторов
  тянет тяжёлые контейнеры и ломает лимит сборки.
- **MUST:** после возврата — загрузка исправленного файла одной кнопкой прямо с экрана
  замечаний, это новая версия. Плюс правка полей и метаданных в форме — та же форма,
  что нужна для ручного ввода при недоступной модели.
- **Исправление поля — это исправление файла.** Раньше исправленное поле жило только
  в карточке, а согласующий получал прежний файл и отдельно «исправленные поля». Теперь:
  - **DOCX — «Исправить в файле»:** прежнее значение находится в тексте (по цитате модели, если
    оно встречается несколько раз) и заменяется новым в том же фрагменте — оформление остаётся,
    разметка не трогается (`DocxCorrector`, средствами JDK, без POI). Получается новая версия, и
    модель читает её заново: проверяется файл, а не наши представления о нём. Сомнительное —
    значения нет в файле, оно неоднозначно, занимает несколько абзацев — не трогается, человеку
    называется причина.
  - **PDF** автоматически не правится: исправить исходник и загрузить файл.
  - **«Сохранить, не меняя файл»** — только если ИИ прочитал поле неверно. Такое поле
    хранит `fileValue` (что в файле), и согласующий видит ручную правку: она не прячется.
  - Тип документа, определённый неверно, автор меняет у черновика — версия перепроверяется.
- **SHOULD:** служебную записку можно **создать и править прямо в приложении как форму**
  (адресат, от кого, тема, текст). Тогда быстрая правка — это правка формы, а не файла,
  и модель для таких документов вообще не нужна: поля уже структурированы.
  Версия такого документа хранит содержимое в `DocumentVersion.content`, а не файл.
- **Навигация по замечаниям (SHOULD):** у каждого замечания — дословная цитата
  и страница, если формат её даёт. Цитата проверяется на точное вхождение в текст,
  иначе не показывается. У документа-формы нажатие на замечание фокусирует поле.
  Для замечаний «поле отсутствует» места в документе нет по смыслу — а это самый
  частый вид замечаний.
- **Переписывание текста моделью — COULD и только для документов-форм:** модель
  предлагает вариант, автор сравнивает и явно принимает; ничего не применяется
  автоматически. Результат — новая версия, и правила проверяют её заново.
  Набор плейсхолдеров в ответе обязан совпасть с отправленным, иначе предложение
  отбрасывается: модель не должна терять или подменять данные.
- **Переписывание загруженных файлов моделью — WON'T:** нужна генерация файла,
  теряется форматирование, растёт риск выдумки в официальном документе.
- **Выгрузка записки-формы в файл (DOCX/PDF) — WON'T:** текст записки целиком на
  карточке, отдельный файл продукту не нужен; не делаем ни до, ни после сдачи.

### Правила проверки компании

Справочник правил — **шаблон сервиса**, одинаковый для всех; компания хранит только отличия от него
(`organization_rule_setting`), правила не копируются. Нет настройки — действует шаблон. Администратор меняет в
«Компания» → «Правила проверки»:
- проверять или нет, важность, текст замечания, свой документ-основание и пункт — у любого правила, **кроме закона**;
- ожидаемое значение — только у «Не короче» (число) и «Одно из значений» (список). Шаблоны формата (regex) и формат
  даты не открываем: человек не должен писать регулярные выражения, а ошибка в них молча ломала бы проверку.

Нельзя: менять правила вида `LEGAL` (закон одинаков для всех), создавать новые правила и поля (это данные шаблона).
Рекомендация сервиса, которой компания указала свой документ, становится правилом компании (`INTERNAL_POLICY`).
Шаблон нейтральный («Типовые правила оформления… (шаблон сервиса)»), а «Инструкция по делопроизводству Демо-компании»
— настройка демо-песочницы при создании: так в демонстрации сразу видно «Изменено компанией».

Замечания — снимок на момент проверки: изменённые правила действуют на новые проверки, черновик автор перепроверяет
кнопкой «Проверить заново» (без модели, по сохранённым полям), документы на согласовании не пересчитываются.

### Модель извлекает, код решает

**Языковая модель не решает, нарушено ли требование.** Она превращает
неструктурированный текст в поля и **отдельным вызовом после них** — в краткую
сводку для человека («Кратко от ИИ»). Общий вызов на оба запроса пробовали
он сдвигал модель к домысливанию дат в самих полях (живой прогон GigaChat); разные системные промпты — разные вызовы, а не один. Вызовы идут
**последовательно, не параллельно**: личный аккаунт
GigaChat (`GIGACHAT_API_PERS`) допускает только один поток запросов одновременно,
и два параллельных вызова на документ гарантированно роняли один из них 429
«Too Many Requests» — включая поля, не только сводку. Сначала поля с полным
бюджетом времени; сводка — только в остаток, дополнительно ограниченный отдельным
потолком, чтобы редкий медленный ответ не растягивал загрузку почти до второго
полного тайм-аута. Код отбрасывает сводку целиком, если хотя бы одно число,
записанное цифрами, или дата с месяцем словом не встречаются в документе; поля
сбой сводки не трогает. Дальше детерминированный `RuleEngine` сверяет поля
с правилами из базы.

```
файл → извлечение текста → минимизация → маскирование
     → DocumentExtractor.extract (модель)    → поля
     → DocumentExtractor.summarize (модель)  → краткая сводка (после полей, в их же бюджет времени)
     → RuleEngine (обычный код)   → ValidationIssue[]
```

Почему так: результат воспроизводим и тестируется без модели; проверка работает
при недоступной модели по введённым вручную полям; каждое замечание по построению
ссылается на правило, потому что правило его и породило.

### Порты

| Порт | Ответственность |
|---|---|
| `ai/DocumentExtractor` | Текст → поля + краткая сводка; код проверяет факты сводки |
| `ai/DocumentClassifier` | Текст → вид документа и короткое название. Модель выбирает схему полей, а не оценивает документ. Вместе с `DocumentExtractor` — единственные места, где живёт модель |
| `rules/RuleEngine` | Поля + правила → замечания. Обычный код, без модели |
| `storage/FileStorage` | «Положить файл → ключ», «получить по ключу» |
| `security/MaxIdentityVerifier` | Проверка подписи данных запуска мини-приложения |

Провайдер модели выбирается настройкой `app.ai.provider`; смена на YandexGPT,
OpenAI-совместимый эндпоинт или локальную модель не трогает доменный код.
Отдельного слоя `AiProvider` над Spring AI не заводим — Spring AI **и есть**
этот слой, второй был бы обёрткой над обёрткой.

Правило: **никаких классов GigaChat или MinIO за пределами их реализаций.**

### Подключение компании (онбординг) — MUST

Компания подключается сама, без разработчиков. Засеянная база остаётся только
для демо-организации.

```
Первый вход, не состоит в компании
 ├─ «Создать компанию» → название → создатель получает права администратора и роль «Директор»
 │     → компании автоматически создаются стандартные роли и маршруты
 │
 ├─ Общее приглашение (код компании) — для рабочего чата
 │     многоразовое, без срока; «Перевыпустить» отзывает старый код
 │     → сотрудник вводит код и отправляет заявку — или открывает ссылку с кодом,
 │       и заявка подаётся сразу при открытии → экран «Заявка отправлена»
 │     → JoinRequest (PENDING) → ADMIN получает уведомление в боте
 │     → ADMIN принимает и на том же экране назначает роли — или отклоняет
 │
 ├─ Личное приглашение — для одного человека                         [SHOULD]
 │     ADMIN заранее выбирает роли (кроме ADMIN) → одноразовая ссылка на 72 часа
 │     → человек открывает → видит компанию и роли → «Вступить»
 │     → вступает сразу, без заявки, и попадает на главный экран
 │     → ADMIN получает уведомление «Иванов вступил по вашей ссылке» с кнопкой «Исключить»
 │
 └─ «Открыть демо-компанию» — только при DEMO_MODE=true, личная песочница
```

**Подтверждение зависит от типа приглашения, а не от того, код это или ссылка.**
Код можно переслать в личку, а ссылку — в общий чат. Поэтому правило не «ссылка
без подтверждения, код с подтверждением», а «общее приглашение — с подтверждением,
личное — без». Код компании можно отправить и ссылкой: он всё равно ведёт к заявке.

**Общее приглашение даёт право подать заявку, а не доступ.** Утёкший код не открывает
документы, поэтому он может быть коротким и удобным для ручного ввода.

**Личное приглашение — это предъявительский токен.** Система не знает, кому админ
его отправил: вступит тот, кто откроет первым. Привязать ссылку к получателю нельзя —
идентификатор человека в MAX администратору неизвестен. Поэтому риск утечки
не предотвращается, а ограничивается:
- ссылка одноразовая, живёт 72 часа, неиспользованную можно отозвать;
- роли выбираются при создании ссылки, **права администратора через ссылку не выдаются никогда**:
  она назначается только явным действием на экране участников;
- при открытии ничего не происходит автоматически — нужна кнопка «Вступить»,
  на экране видны компания и роли, которые человек получит;
- администратор сразу получает уведомление о вступлении и может исключить человека
  одним нажатием.

Отсюда вывод для интерфейса: при создании личной ссылки администратор видит
предупреждение «вступит тот, кто откроет первым — отправляйте только в личные сообщения».

Правила:
- `max_user_id` пользователь не вводит никогда — только из проверенной `initData`.
- Роли назначает только ADMIN своей организации — в том числе себе: роли — не привилегии,
  права администратора — отдельный флаг. Себе права администратора снять и себя исключить нельзя.
- В маршрутах участвует только **активный** участник с хотя бы одной ролью.
- **Права администратора — флаг участника (`is_admin`), а не роль.** Роли — только
  предметные (Директор, Юрист…) и используются в маршрутах; администратора нельзя
  случайно поставить согласующим. Отдельной роли OWNER нет: снять права с последнего
  администратора система не даёт.
- Новая компания сразу получает стандартные роли (Директор, Руководитель отдела,
  Юрист, Бухгалтер, Кадровик) и **консервативные** маршруты: необязательные этапы
  пропускаются, если такой роли в компании нет. Поэтому компания из двух человек
  работает сразу. Таблица маршрутов — ARCHITECTURE.md, раздел 5.
- В MVP пользователь состоит **в одной** компании. Схема допускает несколько,
  интерфейс — нет. Заодно это ограничивает спам созданием компаний.

**Обязательные проверки:**
1. Личность — только из проверенной подписи `initData`, с проверкой давности.
2. Токен личной ссылки — криптографически случайный, не короче 128 бит. Код компании
   для ручного ввода — 8 символов без двусмысленных букв, с ограничением числа
   попыток на пользователя.
2а. Использование личной ссылки **атомарно**: один запрос помечает её использованной
   (`UPDATE ... WHERE used_at IS NULL AND revoked_at IS NULL AND expires_at > now`).
   Иначе два человека, открывшие ссылку одновременно, вступят оба.
2б. Личная ссылка не выдаёт права администратора; набор ролей проверяется при
   создании ссылки, а не при вступлении.
2в. Личная ссылка создаётся только ADMIN; при снятии ADMIN с создателя его
   неиспользованные ссылки остаются действительными, но их видят и могут отозвать
   все администраторы компании.
3. Одобрять заявки и менять роли — только ADMIN **той же** организации. Проверять
   принадлежность заявки или участника к организации администратора, а не только
   сам факт прав администратора: иначе администратор одной компании управляет чужой.
4. Заявитель до одобрения не видит ничего, кроме названия компании.
5. Одна активная заявка на пользователя; участник не может подать заявку повторно.
6. Нельзя снять права администратора с последнего администратора.
7. Снять роль или исключить участника можно всегда и сразу, но документ не должен
   зависнуть: документы, где он ещё не решил, возвращаются авторам с отметкой
   `MEMBER_REMOVED`, автор отправляет заново (маршрут подберёт другого носителя роли,
   одобрения остальных сохранятся, если документ не менялся). Раньше действие
   запрещалось, и администратор ждал решения того, кого исключает.
8. Права читаются из базы на каждом запросе, а не кэшируются в сессии: снятая роль
   действует сразу.
9. Перевыпуск кода компании отзывает старый код. Уже поданные по нему заявки
   остаются на рассмотрении — решение по ним всё равно за администратором.
10. Автор не согласует собственный документ, если есть кто-то ещё с нужной ролью:
    при разрешении ролей автор исключается из кандидатов. Если обязательная роль есть
    **только у автора** — шаг создаётся сразу согласованным с отметкой
    `AUTHOR_HOLDS_ROLE`, видимой в истории. Иначе маршрут маленькой компании был бы
    непроходим. Подробно — ARCHITECTURE.md, раздел 5.
11. Переключатель участника в DEMO_MODE работает только внутри **личной песочницы
    вызывающего** и никогда не даёт действовать от имени участника реальной компании
    или чужой песочницы.

Проверка прав на документы — в сервисе, до любой работы с данными и до модели:
активный участник организации документа, и он либо автор, либо у него есть шаг
согласования по этому документу (в любой версии, на любом этапе), либо документ виден
всей организации **и не черновик** — черновик видит только автор, флаг видимости действует
после отправки. Согласующий этапа 2 видит документ заранее, решивший — сохраняет
доступ к истории. **Решать** можно только по шагу активного этапа.

**Идентификатор пользователя берётся только из проверенных данных запуска
и никогда из тела или параметров запроса.** Без этой проверки вся ролевая модель —
декорация.

### Безопасность и работа с ИИ

- Доступ фильтруется по роли и организации **до** модели и **до** интерфейса.
  Не полагаемся на то, что модель «сама не расскажет лишнего».
- **Маскирование именованными плейсхолдерами**, не звёздочками:
  `1234567890 → <INN_1>`, `Иванов И.И. → <PERSON_1>`. Соответствие хранится
  локально и подставляется обратно при показе. Модель видит семантику поля,
  но не значение — при звёздочках она теряет и структуру тоже.
- **Минимизация:** в модель уходит текст, а не файл, и только нужный фрагмент,
  если документ длинный.
- **Сканы без текстового слоя не распознаём — WON'T в MVP.** Распознавание
  изображения (OCR или модель со зрением) ломает маскирование: картинку не заменить
  плейсхолдерами, персональные данные ушли бы в модель как есть. Плюс качество на телефонных
  фото и новая зависимость в сборке. Файл без текста модель не получает вовсе, версия помечается
  `textMissing`, экран говорит «похоже, это скан», поля — вручную, правила проверяют так же.
  После пилота — OCR в контуре заказчика, до маскирования.
- Каждое замечание несёт `rule_id` и источник.
- **Решение по документу модель не принимает никогда.** Только человек.
- **Ноль секретов в репозитории.** Токены — только в `.env` (в `.gitignore`)
  и на служебном первом слайде презентации.
- **Не заявляем соответствие 152-ФЗ.** Обработка у российского поставщика —
  необходимое условие, но не достаточное. В MVP работаем **только на синтетических
  тестовых документах**, и это сказано прямо в README и презентации.

### Статусы документа

`DRAFT → IN_APPROVAL → {APPROVED | REJECTED | RETURNED}`. Из `RETURNED`
новая версия переводит документ в `DRAFT`: автор видит проверку и отправляет заново,
маршрут начинается с этапа 1. Возвращённая версия не редактируется — она в истории.
Полная таблица переходов — ARCHITECTURE.md, раздел 4.

**Показываемый статус** вычисляется в одном месте на бэкенде и отдаётся готовым полем —
карточка, списки, фильтр и бот показывают одно и то же: «Черновик», «На согласовании», **«На утверждении»**
(`IN_APPROVAL`, текущий этап — утверждение), «Согласован» (`APPROVED` без этапа утверждения), **«Утверждён»**
(`APPROVED` с этапом утверждения), «Возвращён», «Отклонён». В базе статус документа прежний. Слова «подписан»
не используем: квалифицированной подписи нет, подпись — точка будущей интеграции, а не наш статус.

Отдельного состояния «идёт проверка ИИ» нет намеренно: это операция на секунды,
а как статус документа она создаёт возможность залипнуть в ней навсегда.
Состояние проверки живёт на версии документа, не на документе.

### Приложения к документу

Документ часто состоит из нескольких файлов: служебная записка или приказ в DOCX
и приложения — например, две таблицы XLSX. Поэтому **версия документа — это набор
файлов**: один основной и до 10 приложений.

**Архив как единица хранения не используем**, хотя идея «согласуется набор целиком»
верная. Против архива: на телефоне внутри мини-приложения его не открыть и файлы
не просмотреть; автору пришлось бы упаковывать zip на телефоне; из архива нельзя
заменить один файл без перепаковки; распаковка на сервере — отдельный класс уязвимостей
(zip-бомбы, обход путей). Список файлов даёт то же «согласуем пакет целиком» без этих
проблем.

Правила:
- Согласующий одобряет **версию целиком** — со всеми приложениями. Шаг согласования
  уже хранит номер версии, отдельная связь с файлами не нужна.
- Новая версия **переиспользует** неизменённые файлы: строка `DocumentFile` копируется
  с тем же `storage_key`, повторно ничего не загружается. Автор после возврата может
  заменить только основной файл или только одно приложение.
- Файлы в хранилище неизменяемы и в MVP не удаляются: на них могут ссылаться несколько версий.
- Извлечение полей и проверка правил — **только по основному файлу**. Приложения
  хранятся, скачиваются и видны согласующему, но не анализируются.
- Типы: основной файл — PDF и DOCX. DOC не принимаем: ИИ его не читает (нужен Apache POI, он не укладывается
  в лимит сборки), на DOC — ошибка с советом сохранить как DOCX. Приложения — ещё XLSX, PNG, JPG. Тип проверяется
  по содержимому файла, а не по расширению. До 10 МБ на файл, до 30 МБ на версию.
- Скачивание — только через бэкенд после проверки прав.

Приоритет: **схема — MUST сейчас** (таблица `DocumentFile` вместо файловых полей
в `DocumentVersion`, иначе потом переделывать миграции); **загрузка приложений в API
и интерфейсе — SHOULD**; правило «приложение такого-то вида приложено» — COULD;
анализ содержимого приложений моделью — WON'T.

### Версии документа

`Document` хранит метаданные и текущий статус, `DocumentVersion` — файлы и признак
чувствительных данных: он относится к содержимому конкретной версии.
Возврат на доработку создаёт **новую версию**, а не затирает старую.

`ApprovalStep` фиксирует, **какую версию** согласовал человек — иначе история
недостоверна: «Иванов одобрил» без указания версии ничего не значит.

Текущая версия — это поле `current_version_no` (число), а не внешний ключ
на `DocumentVersion`: ключ создал бы круговую ссылку между таблицами.

## Интерфейс

Мобильный MAX — основная платформа (360 и 390 px): шапка,
прокручиваемый контент, закреплённые действия снизу; нативных `<select>` нет, выбор — нижней панелью;
одно главное действие на экран; подписи не обрезаются; человеческие формулировки; ошибки — рядом с
действием; цвета статусов — токены. Логика экранов — [SCREENS.md](SCREENS.md).

### Что реально есть в `@maxhub/max-ui` 0.5.0

Проверено в установленном пакете:

`Avatar`, `Button`, `CellAction`, `CellHeader`, `CellInput`, `CellList`,
`CellSimple`, `Counter`, `IconButton`, `Input`, `MaxUI`, `Radio`, `Spinner`,
`Switch`, `Textarea`, `ToolButton`, `Typography`.
Хуки: `usePlatform`, `useColorScheme` и другие.

**Чего в библиотеке нет** — придётся делать самим:
layout-примитивов (Grid / Flex / Container / Panel), модальных окон, селектов и
выпадающих списков, вкладок, загрузки файлов, карточек, иконок (их всего 2).

`Dot` **помечен deprecated** — на нём не строить индикаторы статусов.

`Typography` — это составной компонент: `Typography.Title`, `.Text`, `.Body`,
`.Headline`, `.Label`, `.Display`, `.Action`. У `Title` проп `variant`
(`large-strong`, `medium`, …), а **не** `level`.


## Соглашения по коду

**Общее**
- Комментарии и пользовательские тексты — по-русски. Код и имена — латиницей.
- Не коммитить секреты. Ни временно, ни «потом уберу».
- `package-lock.json` и `pom.xml` коммитятся всегда: кейс требует
  зафиксированный файл зависимостей.

**Backend**
- Слои: `Controller` → `Service` → `Repository`. Сущности JPA наружу не отдаём,
  только DTO.
- Ошибки — через `@RestControllerAdvice`, единый формат ответа. Интерфейс должен
  уметь показать пользователю внятную ошибку: это прямой критерий оценки.
- Никаких обращений к БД из контроллеров.
- Проверка прав — в сервисе, до любой работы с данными.

**Frontend**
- Функциональные компоненты, TypeScript strict.
- Экраны собираются только из дизайн-системы `frontend/src/ui/` (токены и базовые компоненты поверх
  `@maxhub/max-ui`). Цвета, отступы и размеры — токенами, не числами в компонентах.
- Каждый асинхронный экран обязан иметь три состояния: загрузка, успех, ошибка.
- Запросы — на относительный `/api/...`, nginx проксирует. Абсолютные адреса
  бэкенда в коде не прописывать.
